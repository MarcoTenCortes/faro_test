# Faro — contexto para trabajar en este repo

Este fichero es el mapa completo del proyecto para una sesión nueva: qué es, cómo
está montado, cómo fluye cada cosa, qué contratos hay entre piezas, qué
decisiones no se negocian y cómo se comprueba. Léelo entero antes de tocar
código; con esto no hace falta explorar el árbol para orientarse. El README
cuenta lo mismo para personas, con más prosa; `docs/INSTALL.md` es la guía de
instalación y problemas frecuentes. Mantén los tres al día cuando cambies algo:
el paso «docs» de `npm run check` (§2) avisa de lo más fácil de olvidar (número
de pruebas, títulos del registro, mensajes, ficheros del mapa) y `docs.test.js`
comprueba que §10 sigue diciendo lo que dicen los tests. `AGENTS.md` es sólo un
puntero de tres líneas a este fichero (algunas herramientas lo buscan por
nombre): no se mantiene aparte, y `docs.test.js` pina que no se quede atrás.

## 1. Qué es

Extensión de Chrome MV3 («Faro») que convierte un **opencode local** (servidor
headless HTTP+SSE en `127.0.0.1:4096`) en un copiloto dentro de Jira y
Confluence. Chat en panel lateral; el modelo consulta Atlassian a través del
servidor MCP `mcp-atlassian` (sólo lectura) configurado en opencode; la
extensión además **lleva al usuario hasta la respuesta** (despliega el árbol de
páginas de la izquierda y navega una vez) y **subraya en la página** el
fragmento del que habla (Custom Highlight API + overlay en Shadow DOM).

Cinco piezas: la página (Jira/Confluence) · la extensión · opencode · el LLM
(el que tenga opencode; Faro no habla con ninguna nube) · el MCP de Atlassian.

- Sin build, sin dependencias npm: módulos ES que Chrome carga tal cual. Node ≥18.
- Todo en español: comentarios, UI, logs, nombres de test, muchos identificadores
  locales. Nombres exportados en inglés.
- Verificado contra **opencode 1.2.25**. Chrome ≥116 (la protección de
  `use_dynamic_url` del manifest sólo actúa desde Chrome 130; antes Chrome
  ignora la clave y la extensión funciona igual, sin esa protección). El
  usuario real usa un Confluence Data Center propio
  (`confluence.simplprogramme.eu`, fuera de `*.atlassian.net`) y modelos vía
  `github-copilot/*` y `opencode/*-free`.

## 2. Arrancar y comprobar

```bash
npm run check              # sintaxis (node --check) + orden (TDZ) + manifest + 852 pruebas unitarias + docs (deriva docs↔código; sólo si las unitarias pasan)
npm run check:docs         # sólo el paso docs, informe entero (número de pruebas, títulos del registro, MSG, ficheros del mapa); sale con 1 si hay errores
npm run test:integration   # arranca su propio opencode serve (puerto 4123) y ejercita el cliente real
npm run harness            # Confluence de mentira en http://127.0.0.1:5175 (también .claude/launch.json → preview_start "harness")
npm run turn -- [--host h] [--n 1] [--all] [--db ruta]   # el último turno REAL de una sesión «Faro · …» desde una COPIA de opencode.db (Node ≥22.13; el resto del repo sigue en ≥18)
npm run bench              # el metro: cuánto pesa el system de cada escenario y cuánto tardan los módulos puros; NUNCA falla y queda fuera de npm run check
npm run snapshots          # regenera test/fixtures/prompts/*.txt (las instantáneas de los prompts) con el código actual; sólo cuando el cambio de prompt es intencionado, y revisando el git diff
```

- Paso «docs» (`tools/check-docs.mjs`, el quinto de `npm run check`): el número
  de pruebas de README y de CLAUDE.md §2 tiene que ser el real (`registry.length`,
  la «N/N pruebas» de `node test/run.js`); y cada «`x.test.js` (…; N pruebas» de
  §10 tiene que ser lo que registra ese fichero (`porFichero`, medido por
  test/run.js al importar cada test; «N pruebas más» son las añadidas en un hito
  y no se comprueban); cada título de
  `log.(ok|info|warn|error)('Título'` de `src/` tiene que aparecer entre «» en
  docs/INSTALL.md o en CLAUDE.md; cada `MSG.X` tiene que tener RECEPTOR
  (`case MSG.X` en bootstrap.js o service-worker.js, o `=== MSG.X` en panel.js o
  service-worker.js; quien lo manda con `type: MSG.X` es emisor, no receptor) y
  estar en §5, y un mensaje con receptor y sin emisor es aviso (hoy ninguno:
  `CANCEL_PLAN` lo manda desde H2 el botón «Parar» de la tarjeta); cada
  `.js` de `src/` tiene que estar en el mapa §3. Todo es ERROR desde que
  `STRICT` de `tools/check-docs.mjs` está en `{ titles: true, msgs: true, files: true }`
  (2026-09-13, tras sembrar los 37 títulos que faltaban; con `false` sería
  aviso amarillo con lista). `npm run check:docs` da el informe entero con las
  líneas de cada título.
- `npm run turn` copia `~/.local/share/opencode/opencode.db` (+`-wal`/`-shm`;
  en Windows `%USERPROFILE%\.local\share\opencode\`, NO `%LOCALAPPDATA%`) a
  `os.tmpdir()/faro-turn-<pid>`, abre LA COPIA con `node:sqlite` en sólo
  lectura y la borra al acabar (la original no se toca: su mtime no cambia).
  Enseña la pregunta, longitud y 6+6 líneas del `system`, cada herramienta con
  las seis claves de `INPUT_KEYS` enteras en una línea (`jql`, `page_id`,
  `issue_key`, `query`, `title`, `space_key`; del resto sólo el nombre) y 400
  chars de salida, el texto del asistente con «— bloque de anclas (N notas) —»
  delante del JSON («[texto] N caracteres» cuenta el texto ORIGINAL, sin esa
  línea), y el razonamiento sólo por longitud. Una compactación automática de
  opencode (mensaje `user` con una sola parte `compaction`, seguido de un
  asistente con `summary: true`/`agent: 'compaction'` cuyo texto es el resumen)
  NO es un turno: se anota en el anterior como «(compactación automática de
  opencode tras este turno: resumen de N caracteres)» y la cabecera de la
  sesión cuenta «N turnos · M compactaciones de opencode» (antes salía como
  «PREGUNTA (sin texto)» y con `--n 1` tapaba el último turno real). `--db` con
  un directorio o con un fichero que no es SQLite (o sin tabla `session`) da un
  mensaje de una línea y sale con 1 (`dbErrorText`), nunca una traza. La puerta
  de node:sqlite es el propio `import('node:sqlite')` dentro de un try (vale
  también con `--experimental-sqlite` en NODE_OPTIONS), no la versión ni
  `execArgv`. `--host` casa por subcadena contra el título «Faro · host» o la
  línea «URL abierta: …» del sistema; `--all` incluye las sesiones desechables
  (planificador, observaciones, comprobación, índice de …). Es la forma de ver
  QUÉ contestó el modelo de verdad cuando el panel dice algo raro (§7).
- `npm run snapshots` reescribe los 33 `.txt` de `test/fixtures/prompts/` con
  los prompts que el código produce HOY; `prompt-snapshots.test.js` los compara
  byte a byte y, si difieren, falla con la primera línea distinta. Regenerar es
  aceptar: sólo con un cambio de prompt intencionado y revisando el `git diff`.
  Sin `--update` (`node tools/prompt-snapshots.mjs`) sólo lista qué coincide.
- `npm run bench` (`tools/bench.mjs`, H3) imprime el tamaño del `system` por
  escenario —los mismos de `test/fixtures/prompts/escenarios.js`, así que lo
  medido es exactamente lo que se pina byte a byte— en caracteres, líneas y
  tokens **estimados** (caracteres ÷ 4, etiquetado como estimación: no es la
  cuenta de ningún proveedor), y la mediana de 20 repeticiones de los módulos
  puros más pesados (`normalizeNumbering` sobre el informe real, `matchBlock` en
  su peor caso, `findQuote` literal y difusa, `mergeIndexKeepingTree` con 2 000
  páginas contra 2 000, `parseAtlassianUrl` × 1 000). No tiene umbrales, no
  falla nunca y está FUERA de `npm run check` a propósito: los tiempos de una
  máquina no son un contrato, se comparan dos ejecuciones de la MISMA máquina.
  Hoy: `system` de 2 767 a 29 159 caracteres (mediana 8 127 ≈ 2 000 tokens
  estimados) y ningún puro por encima de 5 ms.
- Extensión: `chrome://extensions` → modo desarrollador → cargar `.` (id fijo
  `ickohiffpicdfeameogbihbcanbjibmk`, derivado de `key` del manifest). Tras

- opencode: `opencode serve --port 4096 --cors chrome-extension://ickohiffpicdfeameogbihbcanbjibmk --print-logs --log-level INFO`
  con `OPENCODE_SERVER_PASSWORD` (la misma en Ajustes del panel).
- Banco visual: `http://127.0.0.1:5175/` (botón **Autocomprobación completa** o
  `await faroHarness.actions.selfcheck()`), `http://127.0.0.1:5175/harness/panel-preview.html`

Borrados en la revisión de H1 (2026-09-14): `GET_TAB_INFO` (con `tabInfo` del SW: nadie lo mandaba) y `CLEAR` (con su `case` en bootstrap.js; `runner.clear()` sigue, lo usa el banco).

## 6. Contratos de datos
- **Ancla** (`validateAnchor`): `{kind:'heading', headingText}` · `{kind:'text-quote', exact(3..300), prefix, suffix(≤80)}` · `{kind:'block-quote', block(1..9999), hint(≤80, obligatoria), exact('' | 3..300)}`. `ANCHOR_LIMITS.affixMax === DIGEST_LIMITS.hintMax` (pinado).
- **Nota** al content script: `{n, title, kind('dato'|'supuesto'|'hueco'|'contradiccion'|'riesgo'|''), anchor}`; claves exactas pinadas por test SEGURIDAD. Máx 12. El `n` de cada entrada del JSON del modelo vale sólo si es un entero o una cadena `/^\d{1,2}$/` (`noteNumber`; `n: true`, `1.5`, `[1]`, `''` se descartan, y el bloque de anclas vale si ALGUNA entrada tiene número). La respuesta de `MSG.ANNOTATE` (`applyNotes`) lleva `ms` (Number, entero) en sus tres salidas: lo que costó resolver y pintar las marcas, medido desde DESPUÉS del `waitFor` de «que la página tenga texto» (hasta 2 s que no son trabajo de Faro, igual que PAGE_DIGEST deja su espera fuera) hasta justo después de `overlay.annotate(items)`, antes del desplazamiento suave (420-820 ms de animación fija). La salida por `reason:'editando'` es anterior al reloj y devuelve `ms: 0`.
- **Digest** (`MSG.PAGE_DIGEST`): bloques = elementos de bloque (BLOCK_TAGS/BLOCK_ROLES) con texto PROPIO (`buildTextIndex(el,{boundary})`, frontera = bloques anidados y, en una incidencia de Jira, la interfaz), ocultos fuera (`aria-hidden`, sin client rects salvo `display:contents`, o con todas sus cajas fuera del documento por arriba/izquierda, medidas sumando el scroll de la ventana y de cada contenedor que envuelve al elemento), 1-based, topes 30000 chars / 400 bloques / 1500 por bloque, `truncated`. Etiquetas: h1-h6, p, li, celda, cita, código, pie, def, txt. **Ámbito** (`digestScope()`): `{roots:[{el, tag?}], chrome}`; en una incidencia, `roots` son título + módulos y `chrome` la interfaz; en Confluence, `[{el: contentRoot()}]` y `''`. La respuesta lleva además `ms` (Number, entero): lo que costó leer la página —recorrerla en bloques, serializarla y mirar los campos de la incidencia—, medido con `performance.now()` y sin la espera a que la página pinte. Se añade, no sustituye: las claves de arriba siguen siendo las mismas y las respuestas de error (`editando`, `sin-texto`) no cambian.
- **Plan**: `{navigate, mode:'direct'|'assisted', destination:{kind, id, title, url, path}, anchor, steps:[{kind,id,title,url,path,label,action:'expand'|'open'}], explanation}`. `TARGET_KINDS`: confluence-page, confluence-space, jira-issue, jira-project.
- **Índice**: sólo rutas relativas (`toSafePath`); `resolveTarget(index, origin, {kind,id})` reconstruye la URL contra el origen de la pestaña; `ancestryOf` da la cadena de padres.
- **Pick**: texto `{kind:'text', text(≤4000), prefix, suffix, heading, pageTitle, url}` · imagen `{kind:'image', alt, imageTitle, caption, filename, around, image:{url,mime,filename}|null}`.
- **Sitio** (`parseAtlassianUrl`): `{host, origin, product:'confluence'|'jira', cloud, spaceKey?, pageId?, projectKey?, issueKey?, wikiPrefix?}`. `pageId` sólo si es numérico (también en `?pageId=`). `spaceKey` sólo si tiene forma de clave (`validSpaceKey`: `/^~?[A-Za-z0-9_.@:-]{1,255}$/` y `isRealSpaceKey`), decodificada con `safeDecode` (un «%» mal codificado no lanza: la clave se descarta y el resto del sitio —producto, `pageId`, prefijo— sigue); `issueKey`/`projectKey` por `validIssueKey`/`validProjectKey`. Lo que entra en la cabecera del prompt son palabras de Faro, y el espacio va citado entre «».
- **Permisos de sesión** (`SAFE_PERMISSIONS`, permissions.js): lista de `{permission, pattern, action}` con claves exactas `['action', 'pattern', 'permission']`; la primera `{ permission: '*', pattern: '**', action: 'deny' }`, las demás `allow` con los `MCP_TOOL_PATTERNS`. opencode evalúa con la ÚLTIMA regla que casa (`permissionFor(rules, tool, argument)` lo simula: `'allow'|'deny'|'ask'`), así que invertir la lista denegaría el MCP.
- **Memoria** (`normalizeMemory`, en `faro:memory:<host>`): `{entries: [{at, text}]}`, claves exactas `['at', 'text']`, `at` número finito dentro del rango de `Date`, `text` no vacío, tope 40; lo sin forma → `{ entries: [] }`.
- **Tiempos del panel** (`state.timing`): `{boot: '', turn: ''}` — dos LÍNEAS ya formateadas por `timingLine`, no objetos: el Registro sólo las imprime. Sólo en memoria (no se guardan ni entran en ningún prompt); las escriben `bootForSite` y el `finally` de `send()`. Son del SITIO: `refreshTab` las vacía al cambiar de host (`state.timing = { boot: '', turn: '' }` dentro del bloque `if (changedHost)`, junto al índice y el contexto), la del arranque la vacía también la salida «sin opencode», y la del turno sólo se escribe si el turno llegó a mandarse y acabó en el mismo host y la misma sesión con que se pidió. Una foto del cronómetro es `{total, phases:[{label, ms}]}` con claves exactas `['phases', 'total']` y `['label', 'ms']`; las etiquetas se aplanan a una línea y pierden el «·» (una fase no puede fingir otra), se acotan a `LABEL_MAX` (40) y una vacía es «fase»: de una fase sólo salen etiqueta y número, nunca cuerpos, URLs ni claves.
- **Enlace del chat** (`allowedLinkOrigin(href, {origin, linkedOrigin})`): sólo `http(s)` con origen EXACTO igual al del sitio, al del Confluence enlazado o a uno de `EXTENSION_ORIGINS` (`['https://id.atlassian.com']`); otro esquema, subdominio parecido, otro puerto, `host@evil` o relativas → false.
- **Sitio guardado** (`sites[host]`, `saveSite`): `{host, configured, mcpName, product, cloud, jiraHost?, confluenceHost?, skippedKeys?, onboarded?, indexedAt?, model?, skill?, wikiPrefix?, analysisSources?}`. `mcpName` es el del host desde el que se configuró (un host enlazado apunta al de su pareja); `jiraHost`/`confluenceHost` sólo si es OTRO host (`siteRecords`, claves exactas pinadas). `linkedContext` en el estado: `{host, contextMd(''), index(null)}|null` — existe en cuanto hay `confluenceHost` guardado, aunque ese Confluence no esté indexado todavía (`linkedHost()` depende de él); el índice NUNCA se guarda desde Jira.
- **Claves de un producto** (`buildMcpConfig`): `{url, email?, token}|null` por producto; `environment` resultante: `JIRA_URL`+(`JIRA_PERSONAL_TOKEN` | `JIRA_USERNAME`+`JIRA_API_TOKEN`), ídem `CONFLUENCE_*` (Cloud: `CONFLUENCE_URL` = origen+`/wiki`), `READ_ONLY_MODE:'true'`.
- **Páginas base** (`normalizeSources`, en `sites[host].analysisSources`): `{mode:'exclusive'|'open', pages:[{id(/^\d+$/), title(≤200 o «Página N»), path(relativa al sitio o ''), spaceKey|null}]}`; claves de página EXACTAS pinadas; máx `SOURCE_LIMITS.maxPages` (6). `sourcesFromSystem` devuelve `{count, mode}` y `sourcesNote`/`hasSources` aceptan esa forma.
- **Campos de la incidencia** (`normalizeIssueFields`, en `digest.issue`): `{type, status, priority, resolution, assignee, reporter, epic, sprint, fixVersions[], affectsVersions[], components[], labels[]}`, claves EXACTAS (`ISSUE_TEXT_KEYS` + `ISSUE_LIST_KEYS`), valores `clean(…, 120)` con `«»` → `"`, listas ≤ `ISSUE_FIELD_LIMITS.listMax` (10) sin repetir; null si nada vale. `issueProfile` → `{family: 'api'|'bug'|'test'|'epic'|'architecture'|'doc'|'story'|'task'|'', phase: 'cerrada'|'bloqueada'|'en-revision'|'nueva'|'en-curso'|''}`.
- **Confluence enlazado como sitio** (`linkedSite`): `{host, origin:'https://'+host, wikiPrefix, cloud:false}` o null; `sourcesSearchTarget(site, linked)` → `{via:'tab'}` | `{via:'linked', site}` | null.
- **Búsqueda** (`searchPages`): `{ok:true, pages:[{id,title,spaceKey|null,url}], via:'v1'|'v2', ms}` | `{ok:false, reason, status?}`. `SEARCH_LIMITS` `{queryMin 2, queryMax 100, maxTerms 6, defaultLimit 8, maxLimit 20, maxResults 20}`; `SOURCE_LIMITS.queryMin/queryMax/suggestions` los referencian (pinado). CQL: `type=page AND title~"w1" AND title~"w2*"` (comodín sólo en el último término y con ≥2 letras; `"`, `\`, `*`, `?` se quitan).

## 7. opencode 1.2.25: lo comprobado en el binario (no está en ninguna doc)
- `format:{type:'json_schema'}` añade la herramienta `StructuredOutput` y fuerza `tool_choice: required` en TODOS los pasos: el modelo no puede acabar en prosa; sin `StructuredOutput` muere con `StructuredOutputError{retries:0}`; `retryCount` se acepta y **nunca se lee**; el input inválido va a la herramienta `invalid` y el bucle sigue (sólo lo acota el vigilante de Faro); no llega texto antes de la llamada con Anthropic y no hay deltas del JSON. Resultado en `info.structured` y en `state.input` de la parte. → **No usar `format` en el turno del chat** (se pierde el streaming; los modelos pequeños se quedan sin respuesta). Sólo en turnos internos: planificador, indexador, segunda pasada.
- `system` se guarda **por mensaje de usuario** y sólo se manda el del último: sirve para contexto grande por turno (la página en bloques) sin acumularlo.
- Un turno se parte en varios mensajes del asistente (uno por vuelta de herramientas): por eso `runTurn` junta partes y `restoreConversation` agrupa por turno.
- `GET /config` devuelve la configuración entera cargada, `mcp` incluido con el `environment` de cada servidor (`JIRA_URL`, `CONFLUENCE_URL` y las claves EN CLARO). Faro lo lee sólo para `mcpForHost` (hosts) y no lo guarda ni lo registra; el cliente no registra cuerpos de respuesta. Cualquiera que hable con opencode sin contraseña puede leerlo: por eso el README insiste en `OPENCODE_SERVER_PASSWORD`.
- Los MCP sólo se cargan al arrancar; `POST /mcp` responde 200 sin hacer nada. Herramientas propias: `{tool,tools}/*.{js,ts}` en `~/.config/opencode` o `.opencode/`, sólo al arrancar, fuera de `SAFE_PERMISSIONS`; no hay endpoint para escribir ficheros. `POST /pty` y `/session/:id/shell` son RCE: no usar.

- **Permisos** (comprobado en el bundle de `opencode.exe` con `grep -a` y contra un `opencode serve` propio, S1, 2026-09-14): `PermissionNext.evaluate(permission, pattern, ...rulesets)` = `rulesets.flat()` + `findLast` de la regla cuyo `permission` y `pattern` casan → manda la ÚLTIMA regla que casa; sin ninguna, «ask». En el turno de chat cada herramienta pregunta con `merge(agent.permission, session.permission ?? [])`: la sesión va DETRÁS del agente (`build` lleva `{permission:'*', action:'allow', pattern:'*'}`) y manda; detrás de todo, las aprobaciones «always» guardadas del proyecto (tabla `permission` de opencode.db: una aprobación de `bash *` hecha desde la TUI en ese directorio ganaría a la denegación de Faro; Faro nunca crea aprobaciones y rechaza todo `permission.asked`). `Wildcard.match(str, pattern)`: `*` → `.*` (así `**` ≡ `*`), `?` → `.`, resto escapado, anclado, sin mayúsculas, `\` → `/`; «git *» casa «git». El `pattern` de una regla se casa contra el ARGUMENTO de la llamada (orden, ruta, URL, consulta), no contra el nombre; `permission` es el id de permiso de la herramienta (bash, read, edit —también write y apply_patch—, glob, grep, task, webfetch, websearch, codesearch, skill, lsp, todowrite, todoread, question, doom_loop, external_directory, plan_enter, plan_exit); una herramienta MCP se registra como `<cliente>_<herramienta>` (`[^a-zA-Z0-9_-]` → `_`) y pide `permission: <esa clave>, patterns: ['*']`; `StructuredOutput` e `invalid` no piden permiso. `PermissionNext.disabled(tools, agent.permission)` sólo mira las reglas del AGENTE con `pattern === '*'`: las de la sesión no quitan herramientas de la lista que ve el modelo, se deniegan al llamarlas (`DeniedError`, el bucle sigue; en el panel sale como fila de herramienta fallida). `GET /experimental/tool/ids` en 1.2.25: invalid, question, bash, read, glob, grep, edit, write, task, webfetch, todowrite, websearch, codesearch, skill, apply_patch (`patch` y `list` no existen; apply_patch pide `edit`). `POST /session` acepta `SAFE_PERMISSIONS` y `GET /session/:id` la devuelve tal cual y en orden.
- `DELETE /session/:id` (`Session.remove`) sólo borra filas y publica `session.deleted`: NO cancela el turno en marcha (`SessionPrompt.cancel` no se llama). Por eso `deleteSession` aborta antes de borrar si el turno se abandonó por la señal en ESTE cliente (`_abandoned`). `POST /session/:id/abort` sobre una sesión ociosa devuelve 200 `true`.
- `GET /session/:id/message?limit=N` devuelve los ÚLTIMOS N mensajes **en orden ASCENDENTE** (el más viejo primero), igual que sin `limit`: comprobado el 2026-09-19 en `test:integration` sobre una sesión de 3 turnos (6 mensajes; `limit=2` devolvió exactamente los dos últimos por `info.time.created`). En las cadenas del binario no se pudo leer (un juez de la auditoría del 2026-09-13 encontró un `reverse()` y el otro no), así que la ventana de la restauración (H6) puede fiarse del orden y `sortMessages` queda como red, no como parche.

- **Lo que costó un turno** viaja en el mensaje del asistente: `info.tokens` = `{total, input, output, reasoning, cache:{read, write}}` e `info.cost` (número). ## 8. Decisiones de diseño (no negociables sin motivo escrito)
1. El panel es el único que habla con opencode; el content script sólo recibe órdenes validadas.
2. El stream SSE vive en el panel (el SW se duerme a los 30 s).
3. El modelo nunca emite URLs ni selectores: identificadores que el panel resuelve contra el índice; validación (`validatePlan`, `validateNotes`, `validateAnchor`) antes de que nada llegue a la página; mismo origen obligatorio. Y lo que devuelven las herramientas tampoco entra a ciegas en el índice: una URL de otro host se blanquea antes de las regex (`dropForeignUrls`) y una clave con forma de incidencia sólo se cosecha si su proyecto es conocido o viene en `/browse/` (S6/M4, 2026-09-14). Los enlaces de la prosa del chat sólo se abren si son del sitio de la pestaña, de su Confluence enlazado o de `id.atlassian.com` (`allowedLinkOrigin`, S5): un enlace que el modelo escriba —o que una página inyectada le dicte— no puede llevar a otro sitio. Y el que no se abriría ni siquiera se pinta como enlace: `renderMarkdown` recibe `allowHref` y lo deja en texto con su URL a la vista, sin `href` ni manejador, porque un `href` con `target=_blank` se abre con el clic central o desde el menú contextual sin pasar por `openUrl` (revisión adversaria de H2, 2026-09-14).
4. El camino es la rama del árbol leída por la API REST del propio Confluence (`learnAncestry`), no lo que diga el modelo; si no hay camino, se lleva de golpe (nada inventado).
5. Un paso intermedio nunca navega: despliega. Sólo el destino abre página.
6. Estructura del árbol como datos (padre-hijo), nunca HTML.
7. Pasos localizados por href y ruta, no por clase CSS; la forma del árbol se decide en un solo sitio (`tree-dom.js`), incluido qué es un menú y no una rama (`isMenuTrigger`: nunca se pulsa un disparador de menú, ni en el barrido ni como paso).
8. El foco (scrim) guía por el árbol; al llegar sólo se subraya. Análisis = ese subrayado numerado. **Escape es de Faro sólo mientras hay algo en marcha** (foco de un recorrido, cartel, barra de selección, seguimiento, o el subrayado de una llegada mientras no haya marcas numeradas: `interceptsEscape()`); las marcas numeradas y los filetes son del panel, que los da por puestos y los quita desde «Quitar las marcas» o con la siguiente orden: un Escape nunca borra marcas a espaldas del panel ni se queda con la tecla cuando no hay nada que cancelar. `onCancel` lo instala el ejecutor (`executeStep`, `applyAnchor`) y lo suelta el overlay (`clearAll`, `clearNotes`; `hideCard` no).
9. Análisis: página en bloques ¶ enseñada al modelo; JSON de anclas al final de la prosa; subraya un **script** con una escalera fija; la pista del bloque la pone la extensión; lo que no apunta a un bloque queda sin marcar; segunda pasada sólo como red; nunca re-marcar solo al restaurar. Un análisis nuevo numera desde el 1; lo demás es seguimiento y conserva las marcas. **Y siempre se intenta subrayar, salvo «Sin observaciones.»**: el formato es del modelo, pero la extensión no se rinde por él: reconoce la numeración «a su manera» y la reescribe en local, se fía del JSON si la prosa no numera, trocea la prosa en una pasada aparte si no hay números en ningún sitio, y como último recurso ofrece pedirlo numerado. Marcar de más (unos pasos «1. 2.» tomados por observaciones) se corrige con «Quitar las marcas»; no marcar es lo que el usuario no acepta.
10. Una marca por línea y recortada a su caja (`rects.js`); en código sólo el trazo.
11. El resaltado no toca el DOM del contenido (Confluence es React): Custom Highlight sobre Ranges + overlay en Shadow DOM cerrado colgado de `<html>`.
12. Contenido de Jira/Confluence = información, nunca instrucciones: todo bloque de página va delimitado y con la regla repetida detrás (SELECTION_OPEN/CLOSE, PAGE_OPEN/CLOSE, SOURCES_OPEN/CLOSE; los campos de una incidencia, citados entre «» en una línea y con la regla detrás; y desde H2 también el contexto del sitio, el del Confluence enlazado y la memoria entre sesiones —prosa que escribió el modelo tras leer páginas, o que subió el usuario— con `contentRule` detrás de cada cierre, y el indexador y el resumen de memoria saben al ESCRIBIR que lo que leen es información, S4); lo señalado con el ratón va además citado línea a línea con «> » y sus datos de una línea sin saltos (S3); la clave del espacio se valida (`validSpaceKey`) y se cita entre «» en la cabecera, como las claves de Jira (S2); el panel construye todo con `textContent`; lista blanca de clics (`FORBIDDEN_ACTIONS`: nunca guardar/publicar/eliminar…); la API de Confluence sólo se lee (GET al mismo origen desde el content script o, desde un Jira DC, al origen del Confluence ENLAZADO desde el panel —host guardado por `siteRecords`, nunca del modelo, con permiso opcional sobre ese dominio y `credentials: 'include'`, y `confluence-rest.js` comprueba que ninguna petición sale del origen que se le da—; id numérico validado, o texto de búsqueda del propio usuario limpiado y acotado antes de ser CQL; nunca una URL como texto de búsqueda).
15. Páginas base del análisis: las lee el modelo por el MCP (no van embebidas: la salida de herramientas se arrastra en la sesión → tope 6); el alcance exclusivo se pide por prompt —y la cabecera deja de invitar a leer «otras páginas»— y se vigila a posteriori con `consultedOutside` como LISTA BLANCA (id, URL resuelta, título plegado contra las páginas base y la pestaña; enlace corto, búsqueda, árbol y Jira cuentan como fuera); una URL pegada sólo si es del mismo host y lleva id numérico; sólo se subraya la página abierta (lo que hable de una página base va con `block: 0`); nunca se persiste nada que no pase por `normalizeSources`.
13. Sesiones con `SAFE_PERMISSIONS`: deniega TODO salvo el MCP de Atlassian (una regla `deny` para `*`/`**` PRIMERO y `allow` sólo para `*_confluence_*` y `*_jira_*` detrás: en opencode manda la última que casa, y lo que nazca en una versión nueva —websearch, codesearch, skill— nace denegado; `test:integration` lo compara con `GET /experimental/tool/ids`; S1, antes se denegaban diez nombres y `patch`/`list` ni existían); claves de Atlassian sólo en la config de opencode, nunca en `chrome.storage`.
14. Todo fallo silencioso tiene contraparte visible: cada `log.*('Sin marcas', …)` va con un `noticeNode`/`showPermissionNotice()` (pinado por test); lo que cuelga de una respuesta pasa por `attachToBubble` (el chat se repinta y la burbuja puede estar fuera del documento).
17. Una incidencia de Jira se lee por sus **puntos de lectura** (título, campos, descripción, comentarios, panel lateral útil), no por «el contenedor»: `main` lo envuelve todo, incluida la barra de acciones y el editor. Qué es contenido y qué es interfaz se decide en UN sitio (`jira-issue.js`, como `tree-dom.js` para el árbol), la interfaz es frontera del texto (ni bloque ni dentro de un bloque), y la escalera de marcado es la misma que en Confluence. Cloud sin verificar: si sus selectores no casan, se lee el contenedor de siempre.
18. Una incidencia se analiza según **lo que es**: el tipo y el estado los lee la extensión de los campos en pantalla (`jiraIssueFields`, en `jira-issue.js`, el único sitio que sabe qué forma tiene una incidencia), no el modelo; la familia y la fase se deducen por nombre (es/en) sólo para ELEGIR qué pedirle (`issueBlock`), y lo que ese tipo y ese estado significan en el proyecto se le remite al CONTEXTO DE ESTE SITIO (que el indexador de Jira ya recoge). Lo que no se reconoce no se inventa: se le pide al modelo que lo deduzca él. Sin campos, que los lea con la herramienta. En Confluence, nada de esto entra.
16. Jira y Confluence son dos productos: **un token cada uno** (en DC son dos instalaciones con PAT propio; el token único de antes sólo valía en Cloud), un solo MCP para los dos, y el otro host **enlazado** al mismo MCP (`siteRecords`) en vez de un segundo proceso con el mismo token. La misma Skill habla distinto según `site.product`: en Jira no hay árbol → Búsqueda con JQL, cierre «Destino: CLAVE», `jira-issue` = un salto único (el proyecto NO es un paso), la tarjeta sólo «Llévame»; la incidencia abierta se excluye como destino. Desde Jira viaja el CONTEXT.md del Confluence enlazado (delimitado, `CONTEXT_BUDGET.linked`, detrás del propio) para saber qué páginas mirar; el índice de Confluence NO (otro origen: `validatePlan` lo rechazaría). En Confluence el prompt es byte a byte el de antes.
19. **Lecturas REST sin tokens** (decidida en `docs/PLAN.md` §5; se implementa en H7-H11): lo que la API del propio sitio da exacto y en milisegundos (una búsqueda JQL, el árbol de un espacio, la muestra de un proyecto, los enlaces de una incidencia, lo que viste y lo tuyo) no se le pide al modelo: el modelo escribe prosa y JQL; la extensión ejecuta, pagina, valida y pinta; si la API no contesta, el camino de siempre sigue entero. Procedencia admitida de cada consulta: la llamada real del MCP (`state.input.jql` de `jira_search`), una plantilla fija con parámetros validados, un filtro del propio sitio, o texto del usuario limpiado. Siempre GET, mismo origen, `maxResults` acotado, campos fijos, tope de tiempo, y por un único `getJson`. Un título del DOM NUNCA se convierte en CQL. En Jira Cloud no hay REST de Jira (410): todo por el MCP.
20. **Actividad y sugerencias** (decidida en `docs/PLAN.md` §5; se implementa en H10-H11): la actividad del usuario es suya y local (ids, claves, títulos y rutas relativas; 30 días; sólo hosts configurados; visible y borrable; nunca en un prompt). Sugerir es gratis y explicado: ninguna sugerencia llama al modelo, cada una dice de dónde sale, Faro nunca añade una página base ni manda una pregunta por su cuenta; ir a una recomendación del host propio pasa por el índice y `validatePlan`.
21. **Recursos accesibles desde la web sólo por URL dinámica** (`use_dynamic_url: true` en `web_accessible_resources`; S7, auditoría 2026-09-13): con el id fijo, la URL estable dejaba que cualquier web detectara Faro y leyera `config.js`. El content script carga TODO por `chrome.runtime.getURL()` (que desde Chrome 130 devuelve la URL con el GUID de sesión), nunca con `chrome-extension://<id>` escrito; los patrones expuestos son content/, content/overlay/, shared/, atlassian/ y nav/ (los dos últimos para los módulos REST de H7), y nada de panel/, background/ ni opencode/; `web-accessible.test.js` sigue el cierre transitivo de lo que carga `bootstrap.js` y `test/manifest.js` exige la clave en cada entrada.
22. **Lo que se captura al pedir es lo que manda al terminar**: todo `await` largo (un turno, el indexado, la espera del MCP, el arranque) captura el sitio/sesión/host con el que empezó (`hostAlPedir`, `sesionAlPedir`, `sitio`/`host` de `generateContext`, `pendingMcp.site`, `state.bootToken`) y al volver comprueba si sigue vigente antes de escribir en `state`, en storage o en el chat; lo que ya no lo está se guarda bajo su host (índice, contexto) o se queda en opencode (la respuesta), y se dice en el registro. Un turno en vuelo se cancela explícitamente (`state.turnAbort`) cuando el panel deja de poder pintarlo (cambio de host, Ajustes, sesión nueva), nunca se deja al vigilante (C1-C7).

## 11. Cómo añadir cosas
- **Módulo puro**: `src/<área>/<nombre>.js` con cabecera de porqué, sin DOM al importar; `test/unit/<nombre>.test.js` con `import { test, eq, assert } from '../harness.js'`. `eq` compara JSON: `undefined` desaparece y el orden de claves importa.
- **Mensaje nuevo**: constante en `MSG` (grupo por dirección), `case` en `bootstrap.js` con import perezoso, `.catch(() => null)` en el panel. Y alguien que lo mande: el paso «docs» de `npm run check` falla si ningún fichero lo atiende (`case MSG.X` en bootstrap.js o el SW, `=== MSG.X` en el panel o el SW) y avisa si lo atiende alguien y nadie lo manda.
- **Prompt**: función pura en `prompts.js`/`skills.js`/`notes.js`; conservar las frases pinadas o cambiar el test en el mismo cambio; contenido de página siempre delimitado y etiquetado; y regenerar las instantáneas (`npm run snapshots`) revisando el diff. Un escenario nuevo: una entrada `{id, que, build}` en `test/fixtures/prompts/escenarios.js` (id en kebab) y `npm run snapshots` para crear su `.txt`.
- **Comprobación del banco**: dentro de `selfcheck()` (`harness/harness.js`), `// N. …` + `ok(nombre, condición, detalle)`; `runner.clear(); renderPage('page:200'); await wait(320)` antes; devolver la página como estaba; fixtures calculadas desde el DOM (`observacionesPorBloques(pageDigest())`), nunca ordinales fijos. La numeración es 1..N sin huecos ni repetidos (`docs.test.js` lo pina; una letra —14b, 28b— es una variante, no un hueco) y cada tramo numerado hace al menos un `ok(`.
- **Título de registro nuevo**: una línea en docs/INSTALL.md («Qué significa cada título del registro») y en la lista de §9; si no, el paso «docs» de `npm run check` falla. **Mensaje nuevo**: también en §5. **Fichero nuevo en `src/`**: también en el mapa §3. **Test nuevo**: el número de pruebas de README y §2. Botón: `<button class="rig-btn" data-act="x">` + `actions.x()`. `window.faroHarness` expone `actions, runner, picker, renderPage, PAGES, OBSERVACIONES, pageDigest, formatDigest, observacionesPorBloques, observacionesDeIncidencia`.
- **Pantalla del panel**: `<section class="screen hidden" id="screen-x">` + `showScreen('screen-x')` + ids referenciados desde `panel.js`.
- **Skill que habla distinto en Jira**: en `skills.js`, `system(ctx)` ramifica por `ctx.product === 'jira'` a una función `xxxJira(ctx)` y deja `xxxConfluence()` con el texto de antes, byte a byte (los tests pinan `skillSystem(id, {product:'confluence'}) === skillSystem(id)`); lo que necesite del sitio (`projectKey`, `issueKey`) entra por `ctx` desde `baseSystem`, validado con regex antes de ir al prompt. Lo que cambie en la cabecera va en `productoBlock`/`navegacionBlock(skill, product)` de `prompts.js`, nunca en las reglas de seguridad.
- **Ajuste**: `DEFAULT_SETTINGS` + `migrateSettings` (config.js) + `applySettingsToUi` + `pushSettings` del SW si afecta al content script.
